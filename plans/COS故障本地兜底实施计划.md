# COS 故障本地兜底实施计划

## 已确认行为

- 正常时直接使用 COS，不长期保存本地副本。
- COS 不可用时，新上传原图及新生成的处理图保存到本地，继续正常处理、查看和下载。
- 后台自动补传到原 COS 对象路径，每个对象补传成功后删除对应本地副本。
- 本地存储模式不变；图片地址、处理状态和前端交互不变，不新增状态面板。
- 不下载历史图库。只在 COS 中存在的图片，在 COS 故障期间无法读取，也无法重新处理；不将其解释为图片不存在。
- 用户充值后重试已成功，停止本次 SSH 排障；尚未获得服务器异常堆栈。

## 现有链路

- [上传接口](../backend/app/api/routes/images.py:194)：检查远端对象、保存原图、提交数据库记录、派发图片处理任务。存在性检查和写入的 COS 异常目前会直接冒泡。
- [COS 存储](../backend/app/storage/cos.py)：所有对象操作直接调用 COS SDK。
- [存储工厂](../backend/app/storage/factory.py)：API 和处理任务统一获取存储实例，适合作为兜底接入点。
- [图片处理任务](../backend/worker/tasks/image_tasks.py)：下载原图到临时目录，生成并保存处理图，再记录版本。
- [文件响应](../backend/app/services/image_file_response.py)：存在性检查后读取文件，需支持本地待同步对象。
- [部署配置](../compose.yaml)：API 和处理进程已挂载同一个持久化图片目录。

## 实现方案

### 1. 存储包装层与持久化待办

在 COS 模式下由工厂返回组合存储，内部复用现有 COS 和本地实现。本地兜底文件使用共享图片目录中的独立子目录，避免与普通本地存储、缩略图混用。

以对象路径为单位持久化同步待办，记录上传或删除操作、内容类型及必要的对象修订标识。使用数据库表与迁移，不依赖进程内列表或临时任务消息；服务重启后可继续同步。原图和每个版本处理图独立记录，允许同一图片的部分对象在 COS、部分在本地。

写入优先 COS；仅 COS 服务或网络相关异常触发本地保存，文件流需恢复到写入前位置。本地写入成功且待办持久化后才能返回成功。本地磁盘和数据库错误不伪装成成功，不扩展通用重试框架。

待办只同步已被图片或版本记录引用的完整文件，避免补传与上传事务提交、处理版本提交之间的竞争。文件先写临时位置再发布，后台不读取半成品。

### 2. 上传、读取、处理与删除

- 上传前优先查询现有数据库同名记录和本地待同步对象。COS 对象检查仍保留；若 COS 检查因故障无法执行，则继续本地兜底流程，不把所有远端检查错误全局转换为“不存在”。保留已有数据库唯一约束及重复上传行为。
- 读取待同步对象优先使用完整本地副本，无待同步副本时仍读取 COS。适配原图、处理图、版本图、缩略图以及对外接口中使用存储的链路。
- 图片处理继续使用现有任务，本地原图可直接作为输入；处理图写 COS 失败也落本地。处理成功与同步完成分开，不因为等待补传而把处理标记为失败。
- 没有本地副本的远端读取故障返回明确的存储不可用响应，不错误返回文件不存在。
- 删除图片、过期版本或失败产物时同时取消待上传操作；COS 删除失败则保留待删除操作，恢复后删除远端对象，避免被后台再次上传。
- 相同对象的补传、删除和重新上传使用对象级互斥与修订检查，防止旧补传任务删除新文件或恢复已删除图片；不同对象互不阻塞。读取已打开文件时，清理不能中断当前响应。

### 3. 独立补传进程

新增独立同步服务，复用应用镜像、数据库和共享目录，不占用图片处理任务的执行槽位，也不在 API 请求中等待恢复。

- COS 模式下每 60 秒扫描一批待办，逐对象执行；无需用户手动触发。
- 补传使用原有对象路径，成功确认后才清理本地副本和完成待办。
- 上传失败保留文件和待办，下一轮继续；当前对象失败不让同步服务退出。
- 使用有限的 COS 请求超时和小批量处理，避免故障请求无限等待。
- 清理失败时保留可继续处理的状态；进程中断后允许重新覆盖上传同一路径，不能先删本地再确认远端成功。
- 兼容多 API 进程、多图片任务以及同步任务与用户删除并发，不引入全局串行锁。
- 本地模式不进行 COS 同步，不新增云服务或第三方依赖。

## 验收重点

COS 故障不再阻断可在本地完成的新图上传和处理；COS 恢复后无需人工操作即可补齐远端文件。故障切换不丢文件，不改变现有图片链接及处理结果，不把云存储问题误报为同名冲突或文件不存在。
